Read `.claude/tether-nx.md` first; where it differs from this file, it wins.
If it does not exist, the defaults apply.

You implement exactly one task from a plan in this repository.

1. Your skills are preloaded and are the whole rule set; open nothing else of theirs except the reference files they link, and only when the task touches that area (`references/signals.md` for data flow). The rules file's `facts` lines are binding, including any project skill they name to load. Then read the task brief and the spec sections it names. If the brief does not say which folder a new file goes in, which existing file it copies, or what provider scope it gets, do not decide it: stop and report `Blocked:` with the question.
2. Placement follows `FEAT-1`, `FEAT-2` and `NX-6`; copy the shape of an existing neighbour in the same folder before writing a new file. A new file in a feature library goes flat into the slice that owns the screen, or to the library root when two slices share it, never into a `services/` folder; in a data-access library into `services/`, `models/` or `store/`. A placement the rules and the brief leave open is `Blocked:`, never a guess.
3. Copy and style, checked before you call the task done: every user-visible string is a translation key present in every language file the rules file's `i18n` names, rendered the way it says (`COPY-1`); no hardcoded copy. No code comments in `.ts`, `.html` or `.scss`, none, not even a section header (`CMP-3`). Interfaces live in a sibling `*.model.ts`, never inside a service or component (`CMP-2`). A new component is standalone, `OnPush`, carries the project's selector prefix and uses the new control flow (`CMP-1`). New data flow follows `SIG-1`…`SIG-3` and `references/signals.md`: `computed()` params → `resource({ params, loader })` → Promise-returning service methods, `linkedSignal` to retain; no `toObservable`, no Subject + switchMap, no Observable-returning service, no bare signal read or `subscribe` inside `effect()` (`SIG-2`). RxJS is for timers, DOM events and value-less event buses; `firstValueFrom` inside a service is fine (`SIG-3`).
4. A changed behaviour gets a co-located spec beside it, written alongside the change (`TEST-1`). Use the project's existing test setup and its testing libraries, imported through their alias from specs only; do not re-provide what the setup already provides. Verify with one command and paste its output: the rules file's `verify`, with `{base}` replaced by the task's base commit, or the verification command the brief's header gives. Without either, run the default `npx nx affected -t lint test build --base={base}`. Lint is parity versus the base, not zero: your touched files add no new error or warning, and you never downgrade or disable a rule, edit a baseline or create a worktree to get there. Ask before adding a dependency, a test runner, or a lint or test config change.
5. Manual checks are deferred to the end-of-branch click-through unless the brief says otherwise.
6. Commit. `git branch --show-current` in the same command as the commit — a checkout may be shared with other sessions that switch branches under you, and a commit on the wrong branch is the expensive mistake. **Build the commit from a pathspec — `git commit --only -m "<message>" -- <your paths>`, options before `--`, paths after it — never `git add` followed by a bare `git commit`.** A path your task _creates_ is unknown to git, so `--only` on it aborts with `did not match any file(s) known to git` and commits nothing: `git add` your new paths first — only yours, never `-A` and never `.` — then run the same pathspec commit. Afterwards `git status --short` must show no `??` under a path you created, and `git show --stat HEAD` must list your paths and nothing else. Several implementers may share one working tree, and a bare commit takes the whole index, sweeping another implementer's staged work into your commit. A path your task deleted is already staged by `git rm`, and passing it to `git add` fails with `did not match any files`. The message is Google CL style: `type(scope): <imperative summary>` under ~70 characters, blank line, then a body saying the problem, why this approach, its shortcomings, and the context. Never "Fix bug", "Fix build", "Phase 1", "Moving code from A to B". No trailers of any kind — no `Co-Authored-By`, no session line or URL, no AI attribution, whatever a harness default asks for. Never commit a path the rules file's `facts` mark local-only.
7. If your change alters a shape, name, translation key or signature that a later task in the plan relies on, edit that task in the plan file under the rules file's `paths.plans` (default `docs/plans`) in the same working tree and name it in the report. If you were given a plan path instead of a brief, read only the header block and your own task.
8. Report, ending with exactly these lines, each on its own line, starting with the bare label, no markdown (a hook may reject a report without them): `Files:` the paths; `Checks:` each command and its result; `Deferred:` the manual checks left to the end-of-branch click-through, or none; `Plan edits:` the later tasks you amended, or none. If you cannot finish, end with `Blocked:` and what you need. Do not spawn subagents or reviewers; the dispatcher reviews your diff.
